# Repository-owned improvement loop

Use existing lessons, test evidence and maintenance checkups, not a new store.
Each repository owns its register of decisions in force, baselines, problem classes,
calendar, record locations and measurement command or documented procedure. It also
declares follow-up due dates and whether overdue items fail its closeout check.
This method adds no hook or gate and grants no write or execution authority.

## 1. Record during work

For each delegated job, keep a start row and an end row linked by job ID, with
role, first pass or rework, and a rework reason class: review, integration, brief
or tool. Record end state and reason; write `unknown` when the reason is unknown,
never omit it. Record pauses and what was waited for. For every question sent to
the owner, keep one row with its applicable classes: authority, derivable, minor
or reversible, repeated, or ill-posed, and the pre-question check that let it
through. Keep one row for every correction of a report already sent. Date rows
and link their evidence in the repository's declared locations.

## 2. Measure a stated period

Run the repository's one command or documented procedure. For each indicator,
report a count or numerator and denominator, the baseline, the difference or why
it is not comparable, and evidence coverage (observed versus eligible records,
with gaps). Without evidence, report `not measurable`, never zero.
Suggested indicators are:

- Rework passes / all writer passes.
- Owner questions classified as derivable, minor or reversible, or repeated / all owner questions.
- Non-current records in the live decision directory.
- Merged worktrees and scratch left behind.
- Failure classes found only at integration.
- Brief-premise corrections.
- Report figures corrected after sending.
- Cursor documents over the repository's budget.
- Jobs that ended without a recorded reason.

## 3. Track recurrence

The second evidenced occurrence of the same problem-class ID opens one improvement
item with an owner, sources, first and last occurrence dates, and a follow-up due
date. Close it only with a named mechanical check, a line in a brief or review
template, or an entry in the repository's register of decisions in force, plus
evidence that the remedy would have caught the recorded cases. Preserve the cases
and closure witness in the existing lessons or evidence location.

## 4. Verify in the next period

At each stage or release closeout and periodic maintenance checkup, run the declared
measurement. The next period shows whether each remedied class recurred after the
remedy; reopen its item if it did. If evidence is missing, effectiveness remains
`not measurable`. List open items past their due date. Check that every line in a
repository's decision register, if it keeps one, cites its source. Local policy
sets baselines, classes, calendar and overdue consequences; this shared method
neither creates a register nor imposes a closeout gate.
